# 后台 Bash 任务终态丢失导致一直显示运行

- 日期:2026-08-13
- 状态:进行中
- 范围:`extensions/pi-grok-bash/index.ts`、`pi-grok-adapter`(`background_bash_bridge.rs`、`pi_adapter/tools.rs`、`pi_adapter/events.rs`)

## 问题

Tasks 面板里的后台 Bash 任务经常停在 `running`,时长一路涨到几十分钟乃至数小时,即使子进程早就退出;点 `[x]` 也没有反应。

终态目前**只有一条投递路径**:扩展在 `finishTask` 里调用
`pi.sendMessage({customType: "pi-grok-background-bash/v1", details:{event:"completed", …}})`,
适配器在 `message_end` 事件里解析它并投影成 `x.ai/task_completed`。这条路径在四种常见情形下会整条断掉:

1. **Pi 正在流式输出时终态被塞进队列。**
   `AgentSession.sendCustomMessage` 的分支是:`isStreaming` 为真时,
   `deliverAs:"followUp"` 走 `agent.followUp(msg)`、否则走 `agent.steer(msg)`——**两者都不会当场 emit `message_end`**。
   消息要等 agent loop 跑到"本可以停下"的位置才被抽出并 emit。长任务在模型工作期间结束是常态,UI 因此可以卡住整整一轮。
2. **用户按 ESC 取消时终态被丢弃。**
   `agent.clearAllQueues()` 直接清空 follow-up / steering 队列,排队中的终态消息**永久消失**;
   同时适配器 `events.rs` 的 `suppress_cancelled_stream` 在 `cancelling` 期间会整段丢掉 `message_end`。
3. **`[x]` 杀任务在流式期间等价于没反应。**
   killed 分支 `shouldWake=false` → `{triggerTurn:false}`,流式中落到 `agent.steer(...)`,同样不 emit `message_end`。
   Pager 侧 `pending_kill` 只等 `task_completed` 来清除,于是永远停在 "stopping"。
4. **会话替换 / RPC 重启后残留行永不收敛。**
   `AgentSession.dispose()` 会 `invalidate()` 扩展运行时,之后 `pi.sendMessage` 直接抛错。
   这个异常发生在 `finishTask` 的 `task.log.end(cb)` 回调里,**回调剩余部分(foreground settler、waiters、`control.sync`)全部不执行**。
   Pi 子进程崩溃重启(20260811 的 `recover_rpc_connection`)时更彻底:老进程连同所有子 shell 一起没了,新扩展实例的 `tasks` 表是空的,
   Pager 的行没有任何来源可以收敛,`kill_task` 也只会返回 `not_found`。

即:**UI 终态被绑死在了模型对话队列的生命周期上**,而这两者本来不该耦合。

## 方案

把"给 UI 的终态"和"唤醒模型的消息"拆成两条独立通路。

### 1. 扩展侧带外终态通道(`extensions/pi-grok-bash/index.ts`)

- 新增私有状态键 `__pi_grok_bash_task__`,复用 `ctx.ui.setStatus(key, json)`。
  RPC 模式下 `setStatus` 是**同步 fire-and-forget** 的 `extension_ui_request` 输出(见 `modes/rpc/rpc-mode.ts`),
  不经过 agent 队列、不受 `isStreaming` / abort / `clearAllQueues` 影响,也不会被适配器的取消抑制吞掉。
  这与既有的 `pi-grok-rpc-compat` 队列通道(`__pi_grok_queue_enqueue__`)是同一套既有机制,不新增 RPC、不改 Pi 源码。
- `BackgroundTask` 记录发起该任务时的 `ui`(在 tool `execute` 拿到的 `ctx.ui`);捕获的是 UI 上下文对象本身,
  不是 `ctx`,因此不会在会话替换后触发 `assertActive()` 抛错。
- `finishTask` 顺序改为:先 `publishTaskState`(带外终态)→ 再 `emitCompleted`(模型消息,`try/catch` 包住)
  → 最后 settler / waiters / `control.sync`。任何一步抛错都不能再阻断后面的收尾。

### 2. 适配器消费带外通道(`pi_adapter/tools.rs`)

- `handle_extension_ui` 的 `setstatus` 分支识别 `__pi_grok_bash_task__`,解析出 `taskSnapshot` 后走**与 bridge 消息完全相同**的投影
  (`background_bash_output_update` + `x.ai/task_completed`)。
- 两条通路都可能送达同一个终态,因此引入统一收口 `project_background_bash()`:
  适配器维护 `background_bash_tasks: HashMap<task_id, BackgroundBashTask>` 镜像,
  终态**只投影一次**,重复的直接丢弃(否则 Pager 会 push 两个 "Task completed" 块)。

### 3. Pi 子进程退出时的终态对账(`pi_adapter/events.rs`)

`adapter_process_exit` 时(无论 intentional 与否,子 shell 都随老进程一起没了):
对镜像里仍处于 running 的任务,合成 `x.ai/task_completed`,`signal: "session_restart"`、`exit_code: null`。
这是 Pager `handle_task_completed` 里**已有**的 `stale_on_load` 语义:行离开 running 过滤器、结束跳动的 bullet,
但**不**往 scrollback 里推一条新的红色 "Task failed"(那是上一个进程生命周期的事,不是现在失败)。

## 不做

- 不改 Pi 源码、不新增 RPC 命令。
- 不新增 Pager UI 面板或第二套任务视图;全部复用既有 `x.ai/task_completed` 通路与 `stale_on_load` 渲染。
- 不做适配器侧轮询/定时对账;终态仍由扩展推送,适配器只在进程退出这个确定性事件上兜底。
- 不改 killed 任务是否 steer 进对话的既有语义(只补 UI 通路)。

- `./scripts/cargo-shared.sh test -p xai-grok-pager-bin --bin grok-pi`
- `./scripts/cargo-shared.sh check -p xai-grok-pager-bin --bin grok-pi`
- 新增单测:带外状态负载解析;终态去重(bridge + 状态通道同一 task 只投影一次);
  进程退出对账产出 `signal: "session_restart"` 的合法 `TaskSnapshot`;扩展源码含新通道常量。
