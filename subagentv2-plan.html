Subagent V2
队伍能力增强方案

01 / THE IDEA

先完善协作语义，再扩展执行边界

当前 V2 已有可工作的协作底座。最有价值的增强是让每次委派拥有清楚的角色、输入、交付物和可回溯记录。

01 — ROLE

角色可发现

基于现有定义加入专业角色，展示职责、来源与能力；继续允许全局和项目覆盖。

02 — HANDOFF

交接可理解

把目标、背景、约束、验收和产物引用变成可选的结构化字段，保留文本入口。

03 — TRACE

过程可追踪

在现有运行记录和 Pager 上呈现责任、交接、等待和结果；历史回放与恢复明确区分。

建议首发边界：先交付单进程团队协作、结构化交接和历史可读；跨重启自动续跑、文件系统强隔离与复杂依赖调度独立设计，不阻塞首版。

非目标：重写 Pi agent loop、创建第二个 TUI、改变 Pi 会话格式、默认启动固定队伍、把提示词当安全边界，或自动重试可能产生外部副作用的操作。

02 / BASELINE

现状与 Alma 对标

以下“现有”来自项目源码静态阅读；Alma 信息基于本机安装包的打包实现，不能替代对其全部运行时路径的验证。

能力本项目现有借鉴与设计方向
角色general-purpose、explore、plan；支持 Markdown 角色覆盖。增加清晰的专业角色和目录。Alma 将角色 profile 映射到执行模式并注入职责。
团队与通信团队预设、稳定代理路径、嵌套 spawn、同伴消息、follow-up、等待、中断与报告。继续使用现有 V2 工具，按需派发；不把所有任务变为固定流水线。
交接主要通过自由文本交付任务，team_report 包含结果状态和摘要。可选 handoff 字段保存目标、上下文、约束、验收及产物；Alma 有类似结构。
可追踪性Pi child session、run sidecar、桥接事件及 Pager 视图；协调器和队列在进程内。关联任务、交接、运行及结果；先支持历史回看，恢复另行设计。
权限内置 explore / plan 的只读主要依赖提示；现有只读模式仍有 Bash。区分“约定只读”和宿主强制权限，不把角色关系当授权。

本机 Alma 的 delegatesTo 已确认用于角色说明与路由提示；未验证它本身是强制授权名单。本方案的任何强制限制都需由项目自身实现和测试。

  • Pi 负责：模型、工具调用、agent loop、会话与上下文；不直接编辑 Pi JSONL 来模拟能力。
  • V2 扩展负责：角色解析、handoff 校验、团队协调、任务身份和状态变更。

04 / PROFILES

角色层：定义职责，保留覆盖

建议首批提供五个面向日常研发的角色；产品管理与运营可按真实需求扩充。角色是配置与提示的组合，不天然拥有新的执行权限。

角色责任与交付建议默认行为
developer实现、定向验证、说明变更和遗留问题。按任务写入；与其他写入者明确文件所有权。
researcher代码侦察、资料查证、来源与不确定性。约定只读，输出可核对的证据。
reviewer独立审查 diff、测试和风险；报告可复现问题。约定只读；可在授权范围执行验证。
designer交互、布局、文案和设计决策。默认调查；需要产出文件时明确写入范围。
planner技术方案、依赖、实施顺序和验收标准。约定只读，除非任务明确授权编写方案文件。

定义与解析规则

  • 沿用 project > global > builtin，保留现有角色与 research、implementation、review 预设。
  • 可增加 mission、focus、deliverables、delegates_to 等元数据；角色 ID 稳定，显示名可本地化。
  • 同名定义解析、禁用和无效配置继续遵循现有行为；展示生效来源。新字段兼容旧 Markdown，安全相关的未知策略不得静默变宽。
  • delegates_to 首版作为提示，不表示权限；若后续改为强制策略，需单独定义继承、拒绝和兼容语义。
  • 对每次 run 记录生效角色来源与配置摘要；配置改变仅影响后续创建的 run，避免历史解释变化。

现有主动协作规范约束子代理默认不继续主动 fan-out；新增角色不改变这一行为。角色仅在任务明确要求时进一步委派。

05 / HANDOFF CONTRACT

结构化交接：可选、版本化、可回传

扩展 spawn_team_agent 与 team_followup_task：保留现有必需的 message，新增可选 handoff。spawn_team 可在后续扩展团队级公共字段；先定义明确的模板合并顺序。

{
  "task_name": "reviewer",
  "agent_type": "reviewer",
  "message": "审查认证改动",
  "handoff": {
    "schema_version": 1,
    "goal": "检查登录及令牌刷新回归",
    "context": ["实现者正在修改认证模块"],
    "constraints": ["只读审查，不修改文件"],
    "deliverable": "按严重程度报告有证据的问题",
    "acceptance_criteria": ["覆盖失败和过期场景"],
    "artifact_refs": ["src/auth/"],
    "write_back": "summary"
  }
}

这是拟议参数示例，不是当前工具已支持的 API。路径为示例；write_back 可定义为 summary / artifact / decision / patch，具体值应与实际处理能力对齐。

校验、注入与关联

  1. 结构化字段可选；缺失时保持原始行为。对提供的字段做类型、长度、版本校验，错误直接反馈调用者。
  2. 由宿主生成 task_id、handoff_id、run_id；不信任模型自行伪造身份或权限。
  3. 将 handoff 以明确分区拼接到子代理上下文，保留原始字段和引用；路径引用需按宿主既有访问规则解释，不自动授予访问权。
  4. team_report 在现有状态和摘要基础上可选增加证据、产物与未完成项；旧结果标为非结构化，不能据此推断验收通过。
  5. 跟进任务产生新的任务/交接 ID 并关联同一代理路径；一次新 run 仍拥有新的 run ID。同一交付重复到达应可识别和去重。
不要提前承诺：acceptance_criteria 是可供检查的任务条件，不等于系统已自动验证；依赖字段首版最多用于展示，只有实现调度和环检测后才能声明为强制依赖。
06 / LIFECYCLE

身份、状态与调度

分开表达“谁”“哪次运行”和“交付是否完成”。稳定代理路径不等同于某一次 run，也不等同于任务 ID。

对象身份与状态关键规则
Agent稳定 /root/… 路径，关联角色及 child session。follow-up 可以激活同一 session，但不复用旧 run 身份。
Run每次激活的新 run ID；排队、运行、完成 / 失败 / 取消。run 终态不可静默复活；排队取消后不得再启动。
任务交付沿用 ready / waiting / blocked / failed / dropped。blocked 必须有问题；waiting 必须有待完成的自身子代理。
重启中断历史记录标识 interrupted。不能把旧进程中未完成的 run 显示为仍在运行。

等待子代理时，当前 turn 应结束以释放并发槽；收到子结果后再激活。保留现有队列语义和去抖消息投递。后续可增加每棵树的深度、成员数、队列和时间预算，且不得突破宿主上限；现有默认后台并发为 25，max_turns 为软上限。

取消：首版保留单代理中断语义。级联取消应作为显式操作，列明受影响后代，记录请求并逐一确认结果；考虑排队、运行、超时和迟到结果，不把外部命令终止当作必然成功。

07 / PERSISTENCE

持久化：先可回看，再谈恢复

现有 child session 保存对话，sidecar 保存运行快照与关联，桥接事件驱动视图。建议先复用现有结构增补可选的交接索引；若需要完整状态日志，再引入独立版本化 journal，避免改变旧 sidecar 的含义。

建议对象关键字段用途
任务 / 交接task_id、handoff_id、发起路径、目标路径、角色、契约版本、时间串起委派、责任人和任务书。
运行run_id、task_id、agent_path、session 引用、状态、时间区分同一代理的多次激活。
结果 / 事件event_id、序号、类型、目标 ID、结果摘要、引用按稳定顺序回看并处理重复事件。

一致性与隐私

  • 每个根会话的协调写入应有单写者约束；不能依赖墙钟排序。遇到损坏尾部或未知版本，保留原数据并报告可读取范围。
  • 如未来需要崩溃后继续交付消息，采用持久化意图、delivery ID 与接收端去重；跨 journal 和 Pi session 不承诺无条件 exactly-once。
  • 首期重启后只承诺历史可读和中断可见；显式恢复须验证 session、运行代次、权限和未完成投递。不得自动重放结果不确定的外部操作。
  • 只记录交接与结果所需数据；敏感引用按既有宿主边界读取，避免在事件、指标和摘要中重复保存密钥。保留周期及清理策略随 journal 设计确定。
08 / EXPERIENCE

界面：复用已有控制面

DIRECTORY

角色与预设

展示角色使命、实际来源、能力和覆盖；从现有角色或团队入口选择，不强制预建团队。

TEAM TREE

团队与运行

展示路径、角色、任务摘要、状态和最近活动；继续进入已有 child transcript。

HANDOFF

任务与结果

查看任务书、验收、等待问题、交付物和证据；区分历史中断与实际运行。

从已有 /subagent-teams、控制中心和 Pager 视图渐进扩展。blocked 的问题要关联来源及后续投递状态；无强制权限时显示“约定只读”。避免展示无依据的验收通过或“可恢复”标记。

09 / BOUNDARIES

权限与写入边界

当前限制：删除 edit / write 工具而保留无限制 Bash，不能保证只读。现有 explore、plan 主要依赖提示约束，不能宣传为沙箱。
  1. 首期：角色和任务明确写入者、路径范围及约定只读；在界面展示实际可用工具和继承配置。
  2. 后续权限层：若要强制控制，先定义宿主策略、父任务授权与角色策略的收紧关系；对 shell、网络、扩展工具和间接写入分别验证。
  3. 共享工作目录：当前没有自动 worktree 隔离，多写入者可能冲突；先规定唯一写入者和交接边界。隔离完成前不承诺自动合并。
  4. 降级：目标平台缺乏可验证强制机制时，应明确显示未强制隔离；不得悄悄扩大权限或把提示标签当保证。
10 / COMPATIBILITY

兼容、迁移和回滚

  • V2 保持现有 opt-in 开关；V2 打开后按现有行为使用 V2 工具面，不能误称 V1/V2 同时注册。
  • 旧 agent Markdown、团队 JSON、字符串任务、现有 team_report 均无需迁移即可工作；新字段默认可选。
  • 保持现有角色覆盖与无效高优先级定义的遮蔽语义；不因无效定义回退到更宽松权限。
  • 旧 session 与 sidecar 按旧格式读取；新记录版本化。旧数据缺失结构化字段时展示“未提供”，不推测交接、权限或验收。
  • 新增 TS 模块、内置角色或资源时，同步检查 Rust 注入器的嵌入物化清单和测试；遵循 GROK_HOME 与 GROK_PROJECT_DIR 的配置隔离。
  • 回滚时关闭新能力或维持 V2 关闭，保留既有 session 与新日志；旧版本不得覆盖无法理解的新数据。具体降级策略须在实现中验证。
11 / DELIVERY

实施顺序与可验收结果

复杂实现先在 docs/issues/ 建立记录；每一阶段完成后更新记录、文档与实际验证结果。以下是建议顺序，不是已完成工作。

PHASE 01

专业角色与目录 最小可交付

扩展角色元数据、内置专业角色及来源展示，按需更新团队预设。

  • 新角色可发现、选择，覆盖和禁用规则符合现有行为。
  • 旧角色和三个预设无须迁移；约定只读标签准确。
PHASE 02

结构化交接与结果 核心价值

增加版本化 handoff、校验、上下文注入及可选结果证据，记录身份关联。

  • 旧文本调用保持行为；结构化任务能返回关联结果。
  • 非法字段、未知版本、blocked 缺问题均有明确错误；不会伪造验收。
PHASE 03

历史记录与 Pager 展示

在现有记录上关联交接和 run，必要时引入独立 journal；展示任务、等待、结果和中断。

  • 重启后历史可查，原先运行的记录显示中断；旧记录仍可查看。
  • 截断、未知版本、重复事件与写入失败均可诊断；不宣称自动续跑。
PHASE 04

可靠性与权限硬化 独立设计

按需求加入树预算、显式级联取消、可实施的权限限制，以及必要的依赖调度。

  • 并发竞争不会突破预算；等待释放槽，排队取消不会启动。
  • 直接工具与 shell 绕过均经过验证；不能强制的平台如实显示。
PHASE 05

受控恢复与发布决策 可选后续

先完成持久化一致性与安全评估，再设计显式恢复；验证真实 provider、Pager、兼容和回滚后决定默认策略。

  • 可恢复和不可恢复的任务均有明确原因；不会重复执行不确定的外部副作用。
  • 真实端到端、文档及回滚证据齐备前，继续保持 opt-in。
12 / VALIDATION

测试与验证策略

范围重点场景
角色与兼容覆盖优先级、禁用、无效配置、旧 Markdown / 预设、资源打包。
交接与报告字段校验、旧消息兼容、结构化注入、结果关联、blocked 问题、重复交付。
调度与故障排队取消、等待释放槽、嵌套结果、迟到消息、日志尾部损坏与写入失败。
安全边界能力收紧、角色覆盖、直接写入和 shell 间接写入；区分可验证强制与约定。
真实体验真实 provider 与原生 Pager：团队启动、跟进、等待、取消、历史、中断和回滚。

实施时按改动范围运行最窄测试；修改 Rust 注入器、adapter 或 Pager 时再分别执行相应定向检查。项目现有扩展测试入口示例：

cd extensions/pi-grok-subagents
# 路径替换为当前环境中已安装的 Pi node_modules
env PI_TEST_NODE_MODULES=/absolute/path/to/pi/node_modules \
  node --import ./test-installed-pi.mjs --test --test-reporter=spec *.test.ts

以上为未来实施的验证建议，本次制作方案没有运行这些项目测试。全量验证的既有阻塞应参考实施时的项目验证记录，不沿用历史结果冒充本次通过。

13 / DECISIONS

风险与待定决策

问题建议取舍
首发只读保证先提供约定只读与明确提示；若业务必须强制隔离，需提前单独设计和验收宿主机制。
日志分层先评估现有 sidecar 能否承载索引；需要可靠重放时再决定独立 journal，不提前引入数据库。
任务依赖首版可描述依赖，但不保证调度顺序；实际 DAG 需环检测、失败传播及测试。
并发写冲突首版任务书明确唯一写入者；worktree、合并和清理作为独立能力评估。
角色数量与成本优先五个职责清晰的角色；简单任务直接完成，避免固定队伍和无收益 fan-out。
恢复副作用未确定外部操作是否发生时停止自动续跑，保留证据并交由用户处理。
