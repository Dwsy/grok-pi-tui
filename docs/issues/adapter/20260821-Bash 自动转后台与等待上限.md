# Issue: Bash 自动转后台与等待上限

## Goal

使用一个可配置阈值 X（默认 4.5 分钟）同时控制前台 Bash 自动转后台与后台任务单次等待上限，避免长工具调用跨过模型 prompt-cache TTL。

## 背景/问题

GitHub Issue #4 指出：前台 Bash 可被 Pager 手动 promote，但不会自动 promote；`wait_tasks` / `get_task_output` 也没有统一等待上限。一个被工具调用阻塞的 agent turn 无法被 follow-up 主动打断，因此应让等待工具在 X 到期后返回当前 running 状态，由下一 turn 继续等待，而不是新增后台 heartbeat。

## 验收标准 (Acceptance Criteria)

- [x] WHEN 前台 Bash 持续运行超过 X，系统 SHALL promote 同一 subprocess 到现有后台任务 UI，不重跑命令，并让前台工具调用返回后台 task_id。
- [x] WHERE `wait_tasks` 或带等待的 `get_task_output` 阻塞，系统 SHALL 把单次有效等待上限钳到 X；到期仍运行时返回 `running`，允许 agent 下一 turn 重试。
- [x] WHERE `PI_GROK_BASH_MAX_WAIT_MINS` 未设置，X SHALL 默认 4.5 分钟。
- [x] IF X 为 0 或负数，THEN 自动 promote 与等待上限 SHALL 关闭并保留旧语义。
- [x] WHERE CLI 与环境变量同时提供，`--bash-max-wait-mins` SHALL 高于 `PI_GROK_BASH_MAX_WAIT_MINS`，环境变量高于默认值。
- [x] WHERE Bash 自身显式 `timeout` 存在，进程终止 timeout SHALL 与 auto-background 相互独立，先到者先生效。
- [x] WHERE 任务显式 `is_background:true`，系统 SHALL 不为其额外安装 auto-background timer。
- [x] WHERE session shutdown / task finish / promote，系统 SHALL 清理 auto-background timer。

## 关键决策

| 决策 | 理由 |
|------|------|
| 单一 X 同时控制 auto-background 与 wait cap | 与 GitHub Issue #4 一致，避免两个易漂移的配置。 |
| 不做 heartbeat follow-up | 当前 tool call 阻塞时 follow-up 不能中断它；等待工具自行到期才是正确唤醒边界。 |
| 复用现有 `task.promote` | 保证同一 subprocess、同一 task UI，不引入重跑风险。 |
| `0/负数` 映射为 `undefined` | 明确表示 feature off，并恢复原先无限等待/仅手动 promote 语义。 |
