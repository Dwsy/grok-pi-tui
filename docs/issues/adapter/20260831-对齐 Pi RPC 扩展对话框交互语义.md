# Issue: 对齐 Pi RPC 扩展对话框交互语义

## Goal

让 Pi RPC 的 `ui.select` / `ui.confirm` / `ui.input` / `ui.editor` 在 Grok 原生 `QuestionView` 中保持 Pi 的阻塞、提交、取消和超时语义，同时不改变普通 Grok `ask_user_question` 的交互。

## 背景/问题

adapter 已把四类 Pi `extension_ui_request` 映射到 `x.ai/ask_user_question`，并用 `pi-extension-ui:<id>` 作为 namespaced `toolCallId`。但 Pager 对普通 QuestionView 的 `Esc` 是分层退栈：退出输入、取消选择、最后 park 到 scrollback；这不会向 ACP `response_tx` 发送 `Cancelled`，因此 Pi 侧 Promise 继续等待，表现为“按 Esc 退出了视觉焦点但 RPC 仍阻塞”。

Pi 原生 TUI/通用 `SelectList` 的 `tui.select.cancel` 默认绑定 `Escape` + `Ctrl+C`，并直接调用 cancel callback。Pi RPC wire type也明确支持 `{ type: "extension_ui_response", id, cancelled: true }`：`select/input/editor` 解析为 `undefined`，`confirm` 解析为 `false`。

## 验收标准 (Acceptance Criteria)

- [x] WHEN `pi-extension-ui:*` QuestionView 收到 `Esc`，系统 SHALL 直接发送 `AskUserQuestionExtResponse::Cancelled` 并关闭卡片，不 park 到 scrollback。
- [x] WHEN Pi `input/editor` 正在文本输入态且收到 `Esc` 或 `Ctrl+C`，系统 SHALL 直接取消并解析阻塞中的 RPC 请求。
- [x] WHEN Pi `select/confirm` 被取消，adapter SHALL 继续使用现有 `{ cancelled: true }` wire response，使 Pi 分别得到 `undefined` / `false`。
- [x] WHEN Pi 对话框超时，系统 SHALL 继续撤销 QuestionView 并返回 cancelled，不留下 zombie overlay。
- [x] WHERE 普通 Grok/ACP `ask_user_question`，系统 SHALL 保持现有 Esc 梯子（input back / unselect / scrollback）。
- [x] WHERE shortcut hints 展示 Pi 对话框 Esc 行为，系统 SHALL 显示 `cancel` 而不是 `back` / `unselect` / `scrollback`。

## 关键决策

| 决策 | 理由 |
|------|------|
| 复用 `pi-extension-ui:` toolCallId namespace | marker 已由 adapter 稳定生成并有测试；避免新增 ACP/client hint 字段。 |
| 仅 Pi-origin QuestionView direct cancel | Pi 原语要求直接 cancel；普通 Grok QuestionView 的 park/unselect 是独立产品交互，不应被全局改掉。 |
| 复用 `submit_question_answers(true)` | 已负责发送 ACP `Cancelled`、恢复 stashed prompt、清理 QuestionView，避免第二套 teardown。 |
| 不修改 Pi core | Pi wire contract 已足够，问题在 Pager 对 Pi-origin card 的键盘语义。 |
