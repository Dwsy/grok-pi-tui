# Issue: 合并上游 e5fd481

## Goal

把 `upstream/main` 的 `e5fd4816d43260c15ba785f103990c1ed6cea230` 集成进 `main`，
并且这一轮必须真正跑 Cargo 验证——上一轮 `75e73f3` 的静态验证边界正是本轮要补上的债。

## 背景/问题

本地 `main` 落后上游 7 个提交（`a5589e9..e5fd4816`）。但仓库里存在一条**已完成冲突解析、
却从未交付**的同步分支 `sync/upstream-75e73f3`，它覆盖了这 7 个里的前 4 个
（`a5589e9..75e73f3`，18 个冲突已逐文件解析）。

关键事实：

| 事实 | 值 |
|---|---|
| `git merge-tree main sync/upstream-75e73f3` | **0 冲突** |
| `git merge-tree main upstream/main`（直接合 7 个） | 38 个冲突文件 |
| `git merge-tree <75e73f3 交付后> upstream/main`（只剩 3 个） | **22 个冲突文件** |
| `sync/upstream-75e73f3` 工作树未提交内容 | 4 个编译修复，未提交 |

那 4 个未提交改动说明上一轮**没有编译过**，只修到一半：

- `theme/pi/map.rs`：上游删除 `Theme::accent_feedback` 字段。
- `app/mod.rs`：`event_loop::run` 新增 `pending_startup: PendingStartup` 参数。
- `settings/defs.rs`：`SettingMeta` 新增 `external_only` 字段。
- `session/workflow/external.rs`：workflow manager 构造新增并发上限参数。

因此本轮策略是**复用而非重做**：先零冲突并入 `sync/upstream-75e73f3` 与那 4 个修复，
以它为基底再合剩余 3 个上游提交，把冲突面从 38 降到 22，同时用 Cargo 关掉上一轮的验证缺口。
