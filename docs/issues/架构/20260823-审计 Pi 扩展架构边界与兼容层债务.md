# Issue: 审计 Pi 扩展架构边界与兼容层债务

## Goal

将 `extensions/*` 中依赖 Pi 私有实现、全局 monkey-patch、临时文件 side channel、重复运行时所有权等架构债务收敛为明确的宿主能力与 typed RPC 边界，同时保留现有用户能力和升级兼容性。

## 背景/问题

2026-08-23 对仓库内 Pi 扩展做结构化审计，覆盖入口规模、tool/command/shortcut 注册、manifest、文件系统/环境变量、session entry、UI host bridge、跨进程传输与实际 grok-pi 注入路径。审计结论表明问题不在“扩展代码多”本身，而在部分能力缺少正式宿主 API 后，通过 process-wide hook 与 side channel 绕过边界。

### 风险分级

#### P1 — `pi-grok-rpc-compat`

- 动态加载 Pi 私有 `core/extensions/runner.js` 与 `core/output-guard.js`。
- process-wide 修改 `ExtensionRunner.prototype.setUIContext` / `getRegisteredCommands`。
- 全局包装 `process.stdout.write`，解析并重写 `get_commands` JSONL 返回，以补充 argument completions。
- 同一扩展还截获 `source=extension` input，将 extension follow-up/steer 队列所有权转交 Rust adapter。
- 单一 shim 同时承担 TUI mode facade、command completion enrichment、queue ownership 三种无关职责，故障域过大且高度依赖 Pi 私有实现。

#### P1 — Remote TUI 与 Rust TUI Bridge 双实现

- 默认 `pi-grok-remote-tui` monkey-patch `ctx.ui.custom`，TS 侧运行 component，通过 widget 投影 frame，并以 temp keyfile/meta file 接收按键。
- 可选 `pi-grok-rust-tui-bridge` 也 monkey-patch `ctx.ui.custom`，但使用 `pi/ui/remote_tui` RPC。
- grok-pi wiring 明确规定 Rust TUI bridge 在 `PI_GROK_RUST_TUI_BRIDGE=1` 时叠加在 remote-tui 上，而非互斥替换；加载顺序为 rpc-compat → remote-tui → shortcut-manager → rust-tui-bridge。
- 两套实现各自维护 active custom session、focus/overlay/layout/component lifecycle，产生双所有权和 wrapper-order 依赖。

#### P1/P2 — `pi-grok-shortcut-manager`

- 再次动态加载并 patch 同一个 `ExtensionRunner.prototype.setUIContext`，与 rpc-compat 形成 wrapper 链和加载顺序依赖。
- primary path 已有隐藏 RPC command `__pi_shortcut_dispatch`，但仍无条件启动 legacy keyfile channel。
- legacy transport 使用 `fs.watch` + 50ms polling；fallback global meta 在源码注释中已标记为 `racy multi-process`。
- 配置写入 `~/.pi/shortcut-manager.json`，没有遵循 grok-pi 的 `GROK_HOME` 产品隔离边界。

#### P2 — `pi-grok-rollback`

- 通过重新构造并 `registerTool()` 覆盖 builtin `write` / `edit` 来捕获 mutation，存在随 upstream tool semantics 漂移的维护成本。
- TS 负责 WAL/blob/session state，Rust 负责 UI/控制面，双方仍通过 control-directory request/response 文件通信，并每 50ms polling。
- 优点：使用 Pi Operations seam、WAL/content-addressed blobs、transactional plan、检测用户覆盖 write/edit 后拒绝继续包装。
- 已核对生产路径：Rust 会注入 `GROK_PI_ROLLBACK_STATE=GROK_HOME/pi-file-rollback`，默认 `~/.grok-pi/pi-file-rollback`；TS 的 `~/.grok` fallback 不是当前 grok-pi 主路径问题。

#### P2 — `pi-grok-workflows`

- Workflow 与 Subagents 都自行管理 child `AgentSession`、capability、cancel、结果回传，存在 runtime primitive 重复。
- hidden spawn/cancel 使用 request/response file bridge；model-facing `workflow` tool 用 `appendEntry` 发 host request 后每 250ms polling response file，最长 4h。
- `appendEntry` 保持控制流不进入 LLM context 是正确方向；问题是 host communication 与 child lifecycle 重复实现。

#### P2 — Todo V2 / Subagents V2

- Todo V2 在 `turn_end` / `agent_settled` 通过 `sendMessage` 发送 steer/follow-up reminder；这是有意影响模型上下文，并非 Recap/BTW 那类应改为 `appendEntry` 的桥接流量。
- Subagents V2 对 root 使用 `pi.sendMessage`、对子 agent 使用 `sendCustomMessage`/resumeRecord，也符合 team messaging 语义。
- 主要债务是 generic `sendMessage` 的队列语义又依赖 rpc-compat 全局 input hook，状态所有权不够显式。

#### P3 — `pi-grok-bash`

- `index.ts` 仍约 650 行，同时承担 Bash、Eval v1/v2、host-tool bridge、background task control、Todo backing event、tool policy 与 session hooks。
- 属于 maintainability / God entrypoint 问题，不是当前最高运行时风险。

### 相对健康的方向

- `pi-grok-auth`、`pi-grok-loop`、`pi-grok-btw`、`pi-grok-recap`、`pi-grok-subagents`、`pi-grok-todo` 已拆成薄 entrypoint + runtime/bridge/UI/definition 模块。
- BTW/Recap 纯桥接流量已改为 `appendEntry`，正确保持 agent-loop context ownership。
- `grok-pi.json` → `HostFeatureManifest` 让扩展 UI/F2 registration 以 extension-owned declarative metadata 为 SSOT，方向正确。

## 验收标准 (Acceptance Criteria)

- [ ] WHEN grok-pi 注入 compatibility extensions，系统 SHALL 不依赖修改 `process.stdout.write` 来扩展正式 RPC schema。
- [ ] WHERE Remote TUI 承载 `ctx.ui.custom`，系统 SHALL 只有一个 canonical component host 与 input transport owner，legacy tempfile 与 RPC bridge 不得同时包装同一 UI context。
- [ ] WHEN extension shortcuts 被发现与派发，系统 SHALL 不依赖 Pi 私有 `ExtensionRunner.prototype` patch 或 50ms tempfile polling，并 SHALL 将 grok-pi 配置存入 `GROK_HOME` 边界。
- [ ] WHERE workflow 与 subagent 创建 child session，系统 SHALL 复用统一的 child-session lifecycle primitive，避免两套 create/cancel/accounting runtime 漂移。
- [ ] IF rollback 需要观察 write/edit mutation，THEN 系统 SHOULD 优先通过宿主 mutation hook/operation observer 获取事件，而不是长期维护一份重新注册的 core tool definition。
- [ ] WHEN synthetic reminder/team follow-up 需要进入 agent loop，系统 SHALL 通过明确的 steer/follow-up host capability 表达队列语义，而不是依赖 compatibility shim 隐式接管 generic extension input。

## 关键决策

| 决策 | 理由 |
|------|------|
| 优先处理 rpc-compat、Remote TUI、shortcut-manager，而不是按文件大小排序 | 三者共同修改宿主私有/全局状态并形成 wrapper/side-channel 依赖，升级与故障影响面最大。 |
| Remote TUI 最终保留单一 RPC transport owner | 已有 RPC 方向可替代 tempfile key transport；双实现叠加没有长期产品价值。 |
| 不把 Todo/Subagents 的 `sendMessage` 一律改成 `appendEntry` | 这些消息本来就需要进入 agent loop；应修的是队列 API/ownership，不是删除模型可见语义。 |
| Rollback 记为 P2 而非 P1 | 当前实现有清晰 WAL/transaction safeguards，且生产状态路径正确；主要问题是长期 seam 漂移和 file polling。 |
| 本 Issue 作为跨扩展架构债务 SSOT，不替代既有单功能 Issue | 既有 Remote TUI、Workflow、Rollback、模块拆分等 Issue 保留各自功能历史，本 Issue 只追踪跨边界收敛。 |
