首轮日志：`/tmp/pi-slim-check-9d7e3490.log`，退出码 **101**。首个明确错误为 `xai-grok-tools/src/tool_taxonomy.rs` 的 `E0117` / `E0116`：`ToolKind` 已移至 `xai-tool-types`，但其 inherent 方法和 `schemars::JsonSchema` 仍在原 crate 实现，违反 Rust orphan/inherent impl 规则。随后的 `E0599` 为同一根因的衍生错误。

## 4. S08b 不宜直接启动的源码证据

- `xai-grok-pager/src` 中 **159** 个 Rust 文件直接引用 `xai_grok_shell::`，其中 `app/` 下约 **87** 个文件；**80** 个 Rust 文件直接引用 `xai_grok_tools::`，其中 `app/` 下约 **51** 个文件。
- `pi-grok-adapter` 仍通过 Shell 的 `session::workflow`、`session::persistence`、`config` 等 API 实现现有单套业务行为。
- 因此简单删掉 Shell/Tools Cargo 依赖会破坏真实 UI/Session/Workflow 绑定，并不等于降低编译成本。

**当前架构裁决：** 冻结原版 Grok MCP 的零散 cfg 增量；保护 Pi Eval MCP、Workflow、Herdr、Remote TUI、Goal、Dashboard、Subagents；仅在当前 HEAD 的 Pi/stock 真实编译和功能回归取得证据后，以当前耗时热点决定是否实施有限 Pager stock/external 分层。不要以重复一套 Agent / Workflow / UI 为代价做“瘦身”。

## 9. 冷构建真实热点：下轮瘦身裁决

冷构建 `cargo --timings` 共 **1,288 dirty units、0 fresh units、4053.4s wall-clock、最大并发 7**，是实际链接的产物而非 `cargo check` 估算。按单元耗时排序（并行任务不可直接相加）：

| crate / 单元 | Total | Frontend | Codegen |
| --- | ---: | ---: | ---: |
| xai-grok-shell | 1236.3s | 521.8s | 714.5s |
| xai-grok-tools | 1219.8s | 230.5s | 989.3s |
| xai-grok-workspace | 959.2s | 359.4s | 599.9s |
| xai-grok-pager | 885.7s | 436.9s | 448.8s |

`xai-grok-tools` **81% 为 Codegen**，不是靠继续删除若干小依赖便能消除。四个 crate 当前物理 Rust 源码分别约 **146,832 / 392,708 / 111,110 / 568,514 行**。另有 `aws-lc-sys` build-script 495.2s、`libgit2-sys` build-script 383.9s、`rhai` 307.8s、`compiler`（Mermaid 库）258.0s，但 Cargo 逆向依赖证明：

- `rhai` 仅由需保留的 `xai-workflow` 引入；**不为了计数拆掉 Workflow**。
- `compiler` 经 `xai-grok-mermaid` 到 Pager，属于原生 UI 渲染的一条真实产品路径，不能仅凭构建耗时直接删除。
- `aws-lc-sys` 经通用 `rustls/reqwest` 多个消费者进入闭包，`libgit2-sys` 经 `git2` 被 Workspace、Agent、fsnotify、代码图使用；简单删除某一个调用方无法立即剪掉整棵依赖树。

**下轮最优先**：从 `xai-grok-tools` 的巨大 Codegen 和 Shell / Pager 大型编译单元中找**共享契约与实际使用的 implementation 边界**，只在有完整调用方映射和收益证据时抽出真正可复用的 crate；不要通过复制 Tool/Workflow/TUI 实现、加大量 stock cfg 或禁用真实产品能力换取表面依赖数下降。后续对比必须同架构、同 profile、同 host、同缓存策略。
