# Issue: 按项目统计模型与斜杠命令使用频率并排序

## Goal

模型选择器与斜杠命令候选使用当前项目自己的累计使用次数排序，跨重启保留，各项目互不影响。

## 背景/问题

当前 `SlashMru` 只持久化 canonical command 的最后使用时间，没有次数或项目身份；补全接受和命令提交均触发记录。模型候选由目录顺序生成并将当前模型交换到首位，搜索只按匹配度排序。

用户于 2026-11-16 11:01（Asia/Shanghai）授权实现“让模型和斜杠命令能按频率、按项目区分排序”。本任务聚焦该能力，不展开旧草案中的 F2 开关。

## 验收标准

- [x] 斜杠命令与动态技能命令累计实际提交次数，一次提交不因接受补全而重复计数。

## 关键决策

| 决策 | 理由 |
|---|---|
| 自动按当前项目使用频次排序 | 对齐用户本次授权，无须新增设置流程。 |
| frequency 为降序主项，同频再比较 recency | 真实表达“按频率”，避免只改名字仍按最近使用。 |
| 查询相关性先于频次 | 常用命令不能压过输入更匹配的候选。 |
| 命令和模型分开计数，模型按稳定 provider/model 身份归一 | 防止名称碰撞、provider 混算及展示名称变更带来的错位。 |
| 计数边界覆盖真实提交/确认后的选择 | 避免 Tab 接受加提交双计数，以及重放、失败切换等被动行为污染频次。 |
| 统计写用户目录而非项目工作树 | 统计是本机状态，不应在任意仓库留下未忽略文件。 |
| 只做非 Cargo 检查 | 根 `AGENTS.md` 明确禁止未获用户请求的任意 Cargo 操作，本次未请求运行构建或 Rust 测试。 |

## 并行审查发现与处理

2026-11-16 的两轮只读审查共指出 9 个问题，全部已修：

1. 两个独立 store 写全量快照会互相覆盖计数 → 改为后台按增量合并，锁内重读后相加。
2. 固定 `.json.tmp` 跨进程会截断对方临时文件 → 改为进程内唯一临时名（`create_new`）并原子替换。
3. 写入失败后增量可能丢失 → 失败批次有界重试，仍失败则保留在写队列并在下一批之前再试；队列满时告警丢弃。
4. `merge_deltas` 里 `key` 绑定在 match 分支内却在分支外使用（编译错误）→ 改为在 match 上整体返回 `(map, key, at)`。
5. 模型候选曾绕过 AppView 注入的 store 走 `thread_local!` 全局 → 恢复为单一注入 store，模型与命令读同一份计数。
6. 模型曾在下发切换前计数，失败切换也会被计入 → 移到 ACP 确认成功处。
7. 四条模型候选入口（Ctrl+L、命令面板、effort 退回模型列表、scoped model 刷新）仍走旧接口导致排序不一致 → 全部改走 `SlashController::suggest_command_args`。
8. 无 session 时的乐观切换已提前改了 `models.current`，确认时判不出“模型是否真的变了”而漏计 → 确认处优先用 `prev_model_id` 判断。
9. 同一微秒内记录两键时 `last_used` 相同，次级排序退化 → 时间戳改为进程内严格单调，增量携带记录时刻，合并取 max。

另外两处顺带修正：锁目录增加归属 token，只删除自己的锁（stale 阈值提高到 300 秒）；排序前按 2 秒节流把项目文件合并回内存，使同一项目的另一个终端的选择也能影响本终端排序。

`router.rs` 中子代理新增的 `available` 闸门会静默吞掉“切到目录外模型”，超出本次范围，已移除。

## 只读审查结论（2026-11-16，独立复核）

审查范围：`git diff`（20 个文件）+ 未跟踪的 `crates/codegen/xai-grok-pager/src/slash/usage.rs`。
方式：只读静态审查，未运行 cargo / 任何构建命令（遵守本次约束）。

### 结论 1 — 阻断编译：`usage.rs` 中 `key` 逃出 match 分支作用域

- 文件行号：`crates/codegen/xai-grok-pager/src/slash/usage.rs:261-266`
- 现象：

  ```rust
  for delta in deltas {
      let map = match delta {
          UsageDelta::Command(key) => &mut file.commands,   // key 只活在这个分支里
          UsageDelta::Model(key) => &mut file.models,
      };
      let entry = map.entry(key.clone()).or_default();       // E0425: cannot find value `key`
  ```

  match 分支的绑定不会逃出分支，`key` 在第 266 行未定义 → rustc 报 `E0425 cannot find value key in this scope`。
  这会让整个 crate 编译不过，新写的所有测试都跑不起来（本次未授权 cargo，所以没被编译器抓到）。
- 为什么错：增量合并是"锁内重读 + 按 key 累加"，`key` 必须在 match 之外可见。
- 最小修法：

  ```rust
  let (map, key) = match delta {
      UsageDelta::Command(key) => (&mut file.commands, key),
      UsageDelta::Model(key) => (&mut file.models, key),
  };
  let entry = map.entry(key.clone()).or_default();
  ```

### 结论 2 — 排序不一致：原生模型选择器有 4 个入口绕过了频次排序

- 文件行号：
  - `crates/codegen/xai-grok-pager/src/app/agent_view/input.rs:1505-1516`（Ctrl+L ModelPicker）
  - `crates/codegen/xai-grok-pager/src/app/modals.rs:78-84`（effort 子菜单退回模型列表）
  - `crates/codegen/xai-grok-pager/src/app/modals.rs:992`（scoped-models 勾选后刷新）
  - `crates/codegen/xai-grok-pager/src/app/modals.rs:1320`（命令面板里敲 `/model`）
  - 对照：`crates/codegen/xai-grok-pager/src/app/dispatch/settings/ui.rs:168-173`（`open_command_arg_picker`，走 `suggest_command_args` → 有排序）
- 为什么错：上面 4 处调用的是 `cmd.suggest_args(&ctx, "")`，而 `ModelCommand::suggest_args`
  （`crates/codegen/xai-grok-pager/src/slash/commands/model.rs:56-58`）固定传 `ProjectUsage::empty()`，
  于是 `build_model_items`（model.rs:180-190）拿到的全是默认 rank → 退化成目录顺序。
  同一个"模型列表"因此有**两种顺序**（`/model` 打开的有频次，Ctrl+L 打开的没有）。
  另外 model.rs:226-234 删掉了"当前模型置顶"的 swap，于是这些未排序入口里
  **当前模型不再在第一行**（改前在）——这是本次唯一一处用户可见的模型列表回退。
- 最小修法：上述 4 处统一改走 `self.prompt.slash_controller.suggest_command_args("model", "", &self.session.models)`
  （面板路径同理），让四条入口共用同一份带频次的候选；或让 `SlashCommand::suggest_args` 不再对
  `/model` 走空 usage（`ModelCommand::suggest_args` 保留给无 usage 上下文的纯函数调用）。

### 结论 3 — 计数边界漏计：无 session 时的乐观切换永远不计数

- 文件行号：
  - `crates/codegen/xai-grok-pager/src/app/dispatch/router.rs:1108-1140`（`Action::SwitchModel` 无 session 分支，
    第 1122 行先 `agent.session.models.set_current(model_id, effort)` 乐观生效，第 1132 行 stash 到 `deferred_model_switch`）
  - `crates/codegen/xai-grok-pager/src/app/dispatch/settings/setters.rs:2160-2169`（`set_default_model` 无 session id 时同样 stash）
  - `crates/codegen/xai-grok-pager/src/app/dispatch/session/lifecycle.rs:1916-1924`（确认点计数处）
- 为什么错：乐观分支已经把 `models.current` 改成新模型。等 session 建好、deferred 切换真正下发并确认时，
  `handle_switch_model_complete` 用 `prev_model = models.current` 判重，此时 `prev_model == model_id`
  → `if prev_model.as_ref() != Some(&model_id)` 不成立 → **这次真实的模型选择不计数**。
  即"确认后才计数"的规则在这条路径上把计数吞掉了（用户显式选的模型没有进入频次榜）。
- 最小修法：要么在 stash 时就计数（与"乐观生效"同一时刻），要么在确认点改用 deferred 里的
  `prev_model_id` 判重，而不是 `models.current`。

### 结论 4 — 排序不稳定：`last_used` 只在"同一 key"内单调，两个新测试会随机失败

- 文件行号：`crates/codegen/xai-grok-pager/src/slash/usage.rs:91-96`（`now_micros`）、`usage.rs:165-168`（`increment`）、
  `usage.rs:268`（`merge_deltas` 里 `entry.last_used = entry.last_used.max(now)`，连 `+1` 都没有）；
  受影响的断言：`slash/usage.rs:374-390`（`assert!(usage.command_rank("help") > usage.command_rank("model"))`）、
  `slash/mod.rs:2586-2600`（`assert_eq!(state.snapshot().matches[0].display, "/plan")`）。
- 为什么错：`increment` 用 `now_micros().max(last_used + 1)`，只能保证**同一 key**严格递增；
  不同 key 之间完全依赖墙钟微秒。连续两次 `record_command` 的间隔只有几百纳秒，极可能落在同一微秒，
  此时两个 key 的 `last_used` 相等 → 频次相同时的"最近使用"次级排序失效 →
  命令落到注册顺序、技能落到小写 display → 上面两个断言随机红。
  落盘合并（`merge_deltas`）连 `+1` 都没有，跨进程读回来的排序比内存里更弱。
- 最小修法：把时间戳改成进程内严格单调：

  ```rust
  static LAST_US: AtomicU64 = AtomicU64::new(0);
  fn now_micros() -> u64 {
      let wall = SystemTime::now().duration_since(UNIX_EPOCH)
          .map(|d| d.as_micros() as u64).unwrap_or_default();
      let prev = LAST_US.fetch_max(wall, Ordering::Relaxed);
      wall.max(prev.saturating_add(1))
  }
  ```

  `merge_deltas` 复用同一个函数（不要用裸 `now`）。

### 结论 5 — 并发下仍可能丢计数：写队列丢弃 + 陈旧锁回收竞态

- 文件行号：`crates/codegen/xai-grok-pager/src/slash/usage.rs:236-254`（`writer_loop`）、
  `usage.rs:313-360`（`FileLock` / `lock_is_stale`）。
- 为什么错：
  1. `merge_deltas` 失败且 `pending.len() >= MAX_PENDING_JOBS` 时，该 delta 被直接丢弃（只 warn）→ 计数永久丢失；
  2. 失败后把 job `push_front` 再 `break`，重试只发生在"下一个 delta 到来"时；用户不再操作则退出进程时 pending 里的计数一起没了；
  3. `lock_is_stale`（30s）会删掉**仍被持有**的锁目录，而 `Drop` 又无条件 `remove_dir` 同一个路径 →
     A 的陈旧回收可以删掉 B 刚建的锁，两个写进程同时进入"读-合并-原子替换"，产生 lost update。
- 最小修法：(1)(2) 改成"失败即阻塞重试 / `recv_timeout` 定时重试"，不做丢弃；
  (3) 锁目录里写 owner pid，只在 pid 已不存在时回收，且持有期间定期刷新 mtime。

### 结论 6 — 次要：新增的 `available` 闸门与本需求无关，会静默吞掉切换

- 文件行号：`crates/codegen/xai-grok-pager/src/app/dispatch/router.rs:1115-1117`。
- 为什么错：计数发生在确认点，这个闸门与计数无关；它把"切到不在当前目录里的模型"变成静默 no-op
  （`set_default_model` 已有同类闸门，settings/setters.rs:2104-2112，但那里带 error 日志）。
  对其它来源的 `Action::SwitchModel` 是行为变更。
- 最小修法：删掉该闸门，或至少加一条 warn 日志并说明"目录外模型"是预期行为。

### 逐项检查结论（无问题的部分）

  `xai-grok-pager-render::util` 转出，存在。
- **计数边界（除结论 3 外没问题）**：命令只在真实提交处计数
  （`app/dispatch/prompt.rs:670`、`app/dispatch/dashboard.rs:1514`）；Tab 接受补全的计数已从
  `views/prompt_widget/mod.rs` 删除，不会双计。模型只在确认成功且模型真的变了时计数
  （`session/lifecycle.rs:1922-1924`），失败 / 回滚 / 只改 effort 都不计。
- **排序键本身一致**：裸 `/` 菜单 = 分组 → 手工标签 → `Reverse<UsageRank>`（频次↓、最近↓）→ 名称；
  过滤搜索 = 匹配分 → 精确归属 → `UsageRank` → builtin → display；
  行内补全 = `build_model_items`（频次排序，`sort_by_cached_key` 稳定）→ `rank_pi_model_selector`（`sort_by` 稳定，同分保序）。
  三条路径用同一个 `UsageRank` 键，频次高于 recency 的次序一致；不一致只发生在结论 2 列出的模型选择器入口。
- **项目隔离没问题**：`SlashMru::roots`（`slash/mru.rs:78-88`）缓存 cwd→项目根，
  `projects` 缓存 根→`ProjectUsage`，所以每次击键只有 2 次 HashMap 查表，**不会重复解析路径**；
  项目身份是"最近的 `.git` 祖先"（含 worktree 的 `.git` 文件），文件名为 canonical 根的 blake3 前 16 位，
  不同项目不同文件、不同内存条目，无串项目。控制器 cwd 随 session 走
  （`PromptWidget::new_with_cwd(session.cwd)`），fork/worktree 处显式 `set_cwd`
  （`session/fork.rs:428,509`、`session/lifecycle.rs:1616`）。
  小瑕疵：`roots` 缓存不失效（事后在子目录 `git init` 仍按旧根归属）且无上限。
- **持久化增量合并的主路径没问题**：锁内重读 + 累加 + 原子替换，两个终端同时用同一项目时不会互相覆盖
  （`usage.rs:374-395` 的 `separate_writers_do_not_overwrite_each_others_counts` 覆盖了这一点）；
  残留风险集中在结论 5。

### 建议的验证顺序

1. 先修结论 1（否则 crate 编译不过，任何测试都无效）。
2. 再修结论 4（否则两个新排序测试随机红，会误判成排序实现有问题）。
3. 修结论 2 / 3 后再补一条端到端断言：同项目内先切模型 A 再切 B，
   `model_rank(A).count == 1 && model_rank(B).count == 1`，且从 Ctrl+L 与 `/model` 打开的模型列表顺序一致。
4. 结论 5 建议单独排期（需要改写线程的重试与锁协议）。
