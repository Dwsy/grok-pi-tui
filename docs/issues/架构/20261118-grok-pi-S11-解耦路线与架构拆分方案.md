#### S12-b2d 前置测绘：`cfg` 级瘦身已到硬边界（2026-11-19 实测）

为判断“继续加 `#[cfg]` 能否让三个 crate 自然退出”，本批对本工作树做了一次静态引用测绘（未跑 Cargo，计数含 `--locked` 编译面已验的部分）：剩余 **69 个未门控文件 / 307 行代码引用**指向 `xai_grok_agent` / `xai_grok_login` / `xai_grok_sampler`。分布排名前六：`agent/config.rs`（33）、`agent/config_tests.rs`（20）、`agent/relay_tests.rs`（18）、`agent/folder_trust.rs`（16）、`remote/skills_client.rs`（15）、`session/slash_commands.rs`（14）。

**阻断点不是 `cfg` 数量，而是 `AgentConfig` 的字段依赖**。实测该结构体直接内嵌了三个重型 crate 的类型：

| 位置 | 字段/方法 | 所属 crate |
|---|---|---|
| `agent/config.rs:1228` | `pub grok_com_config: GrokComConfig` | `xai-grok-login` |
| `agent/config.rs:1260` | `pub skills: SkillsConfig` | `xai-grok-agent` |
| `agent/config.rs:1302` | `pub auth: Option<GrokComConfig>` | `xai-grok-login` |
| `agent/config.rs:1831` | `pub fn create_auth_manager(&self) -> AuthManager` | `xai-grok-login` |
| `agent/config.rs:4751` | `-> Option<SamplerConfig>`（aux 模型解析） | `xai-grok-sampler` |
| `agent/config.rs:3694/3985/4536/4678` | `auth_scheme: AuthScheme` | `xai-grok-sampler` |

而 `AgentConfig` 正是 Pi 侧的核心配置契约：`load_effective_config` → `Config::new_from_toml_cfg` → `AgentConfig`，外部调用点 **229 处**（`pi-grok-adapter`、`grok-pi` bin、`xai-grok-pager`）。

**结论（硬事实，不只影响本批）**：只要 Pi 继续复用 `AgentConfig`，三个 crate 就**不可能**通过继续加 `cfg` 退出 Pi 闭包；`units` 会继续停在 1211。要真正退出，必须做一次 L4 架构迁移：把 Pi 需要的配置子集拆为独立契约类型（不内嵌 `GrokComConfig` / `SkillsConfig` / `SamplerConfig` / `AuthScheme`），在 Stock 侧保留 `AgentConfig` 并补一层转换，同步迁移 229 个调用点，按受控路径刷新 `Cargo.lock`。两条待定路径：

1. **Pi 自有轻量 config 契约（推荐）**：新 `PiSessionConfig` 只携带 Pi 实际读的字段（模型/provider/端点/超时/压缩阀值等），`grok-pi` 与 adapter 改吃新契约；Stock 的 `AgentConfig` 不变。代价：adapter/pager 配置读取层需成批改写，收益是三个 crate 真退出。
2. **Pi 放弃 Stock Agent 浏览与 Sampler 复用**：把 `resolve_agent_definition`、aux 模型 `SamplerConfig` 解析在 Pi profile 下关掉（agents modal 在 Pi 下已是空列表，`build_agent_list` / `format_agent_detail` 已有 `cfg(not(stock-agent))` 分支），仍需处理 `GrokComConfig`/`SkillsConfig` 字段。代价：Pi 侧失去部分 Stock 能力对等；收益：改动面小于路径 1。

上述二选一属于产品与架构取舍，需明确授权后再开工；本批不做静默选择，也不把未实施的拆分表述为已完成。

**阻断面的精确规模（排除三个 crate 自身内部、排除已门控文件与测试文件）**：真正阻断 Pi 闭包的是 **96 个消费方文件**，跨 9 个 crate（`xai-grok-shell`、`xai-grok-pager`、`xai-grok-workspace`、`xai-grok-plugin-marketplace`、`xai-grok-subagent-resolution`、`xai-grok-telemetry`、`xai-grok-http`、`xai-grok-update`、`xai-grok-test-support`），合计 **340 行 `xai_grok_(agent|login|sampler)` 引用 + 257 行重型类型引用**。引用密度前八名：`agent/config.rs`（33+44）、`agent/folder_trust.rs`（16+2）、`remote/skills_client.rs`（15+7）、`session/slash_commands.rs`（14+3）、`agent/remote_config/settings_cache.rs`（14）、`remote/client.rs`（10+10）、`extensions/marketplace.rs`（10）、`session/unified_list/mod.rs`（9+5）。

这组数据的实际含义：三个 crate 退出 Pi 闭包不是“再扫一轮 `cfg`”能收口的量级，而是一次跨 9 crate 的契约迁移。本批已把可安全做的部分（源码级门控 + Pi seam 重路由）做完，不把跨 crate 迁移伪装成同批收尾。

**单 crate 逐步退出也被依赖图堵死（逐个实测）**：

- `xai-grok-sampler`：被 `xai-grok-http`（`src/lib.rs` 2 处）、`xai-grok-telemetry`（`src/http.rs` 1 处）、`xai-grok-login`（`credential_provider.rs` + `attribution.rs` 共 12 处）以**非 optional 硬依赖**引用；`http` / `telemetry` 是 Pi 必需品，所以即使 shell 把 sampler 降为 optional，sampler 仍留在闭包里。仅 sampl 自身的 Pi 侧消费面就还有 `agent/config.rs`(11)、`tools/config.rs`(6)、`session/helpers/*`(2)、`session/summary.rs`(1)、`agent/chat_modes.rs`(1)、`agent/otel_gate.rs`(1) 等未门控点。
- `xai-grok-login`：`AuthManager` 是运行时类型（非纯数据），Pi 闭包内仍有 **224 行 / 52 文件**引用；`GrokComConfig` 及其嵌套 `OidcAuthConfig` / `OAuth2ProviderConfig` / `ForceLoginTeam` / `PreferredAuthMethod` 确实是纯 serde 数据（已验证），但只下沉它们不够——`AgentConfig` 的 `create_auth_manager() -> AuthManager` 仍把 login 钉在闭包里。
- `xai-grok-agent`：`AgentDefinition` 已在 S12-a 判定不可下沉（内含 `ToolServerConfig`、模板、权限、hook、MCP 与动态工具集构造）。

**关于 `Cargo.lock` 的好消息**：已核对锁文件，`xai-grok-shell` 的 lock 依赖列表本来就包含这三个 crate，而 optional 化不改变包解析图（`stock-agent` 仍是可启用路径），**因此降 optional 本身不需要刷新 `Cargo.lock`**。也就是说锁文件不是阻塞点——阻塞点只是那 96 个消费方文件的契约迁移量。

**方法论教训（供后续批次复用）**：

- 手工/静态扫描会漏三类引用：`super::` 相对路径、裸名 re-export（`pub use self::x::*` 后按 `session::NAME` 使用）、以及 **feature 链隐含关系**（`stock-mcp` 是否已隐含 `stock-agent`）。本批最终采用「消费方全量路径 × 定义处门控状态」双向对照扫描，才把 `MEMORY_MODE_META_KEY` 这类仅经星号 re-export 暴露的项抓出来。
- 一次 CI 往返约 12–20 分钟且 macOS runner 有供给风险，错误应在本地静态面尽量收敛，但**不能**用静态推断替代 `--locked` 编译结论。
- 门控改动必须成对核对「被门控模块 ← 谁引用它」和「Pi 侧是否还依赖该符号」，`resolve_agent_definition` 与 `MEMORY_MODE_META_KEY` 都是第二类问题的实例。
- 禁止在尚未证明编译面时派发昂贵的 macOS 验证；先 Linux 边界步、再 ARM64 是这轮唯一有效的止损策略。
