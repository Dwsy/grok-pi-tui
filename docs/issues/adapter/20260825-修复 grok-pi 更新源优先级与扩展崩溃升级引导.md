# Issue: 修复 grok-pi 更新源优先级与扩展崩溃升级引导

## Goal

让 grok-pi 更新检查先使用官方 GitHub 和官方 npm 元数据，最后才使用 JSP 代理；扩展启动崩溃时先引导用户升级 grok-pi，再执行自愈降级。

## 背景/问题

当前更新器先访问 JSP，再访问 GitHub API；两者同时受限时，用户得到代理错误，且没有官方 npm 兜底。扩展自愈遇到启动崩溃时直接移除扩展重启，可能掩盖 grok-pi 本体过旧导致的兼容性问题。

## 验收标准 (Acceptance Criteria)

- [ ] 更新源顺序严格为 GitHub Releases → 官方 scoped npm 元数据 → JSP 代理。
- [ ] 不使用 npm 上同名但属于第三方项目的 `grok-pi` 包；当前官方 scope 包 `@dwsy/grok-pi` 404 时应记录错误并继续 JSP。
- [ ] `✗ Extension crash detected` 后，交互终端默认先询问升级 grok-pi；升级成功则提示重启，不继续使用旧进程自愈。
- [ ] 非交互启动不等待升级输入，仍保持原有自愈流程。
- [ ] 更新器单测、grok-pi Rust 测试、Pi 0.84.3 启动回归和 diff 检查通过。

## 实施阶段

### Phase 1: 规划和准备
- [x] 定位更新源 fallback 和扩展自愈调用路径。
- [x] 验证 `@dwsy/grok-pi` 当前返回 404，确认不能使用 unscoped 第三方包。

### Phase 2: 执行
- [x] 调整官方 GitHub、官方 npm、JSP 的 fallback 顺序。
- [x] 增加 npm dist-tags 版本解析和失败后继续 fallback。
- [x] 在扩展 crash/self-heal 前加入默认升级引导。
- [x] 同步 Feature Matrix / website 更新源说明。

### Phase 3: 验证
- [ ] 更新器单测和静态源顺序检查。
- [ ] grok-pi binary test/check。
- [ ] 交互/非交互崩溃路径审查。

### Phase 4: 交付
- [ ] 更新 Issue 状态与验证记录。

## 关键决策

| 决策 | 理由 |
|------|------|
| 使用 `@dwsy/grok-pi` 作为唯一 npm 候选 | npm 的 unscoped `grok-pi@1.3.0` 属于 `luongnv89/pi-extensions`，不能误装。 |
| npm 只参与官方版本发现，安装仍走 GitHub 官方 installer | 当前官方 npm 包尚未发布；即使未来发布，也避免把包入口与官方跨平台 installer 语义混用。 |
| 升级成功后终止当前启动并要求重启 | 旧 grok-pi 进程的扩展列表和自愈状态不能安全复用，重启才能验证新版本。 |
