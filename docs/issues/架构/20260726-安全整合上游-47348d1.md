#### 2026-08-08 target growth hardening

Repeated local builds later drove generated Cargo output to roughly 200 GiB before manual cleanup. The existing protection only enforced a free-space floor and pruned a bounded number of stale incremental directories; it did not cap total target size. Local Cargo configuration also forced incremental compilation for dev/release builds, amplifying retained object/debug data.

This follow-up changes the repository-managed build path to disable incremental compilation by default and enforce a configurable total target cap. `CARGO_TARGET_MAX_GIB` defaults to 64 GiB; the maintenance path clears legacy incremental caches first and falls back to `cargo clean` for generated output when the cap is already exceeded. The disk guard also receives the target cap so an individual Cargo invocation cannot grow the shared target without bound.

Verification for this hardening:

- `python3 -m py_compile scripts/cargo-maintenance.py scripts/cargo-disk-guard.py` and `bash -n scripts/cargo-shared.sh`: PASS.
- A disposable 1 GiB over-cap maintenance dry-run detected the cap breach, selected the legacy incremental root for removal, and selected `cargo clean` as the fallback if the target remained over cap: PASS.
- A disposable disk-guard run grew a target from below 1 GiB to above the cap; the guard stopped the child process with exit 74 and reported `target reached 1.0 GiB`: PASS.
- `scripts/cargo-shared.sh --version` with an isolated `CARGO_TARGET_DIR`, `CARGO_MAINTENANCE=0`, and 1 GiB guard limits returned Cargo 1.94.0 successfully: PASS.
- No destructive cleanup was run against the real shared target during verification.
