# Issue: 修复 /fork 选择器输入路由丢失

## Goal

恢复 `/fork` 消息选择器的键盘与鼠标输入路由，使选择器重新可确认、可取消、可导航，并用回归测试锁住该接缝，避免下一次上游合并再次丢失。

## 背景/问题

`cargo run -p xai-grok-pager-bin --bin grok-pi` 报出 `handle_fork_picker_key`、
`fork_picker_input_to_outcome`、`handle_fork_picker_mouse` 三个 `dead_code` 警告。
排查后确认这不是死代码，而是**接线丢失导致的功能回归**：

- `/fork` 仍注册在 `slash/commands/mod.rs:331`；
- `dispatch/session/pi_fork.rs:119` 仍会设置 `agent.fork_state`；
- `agent_view/render.rs` 仍会绘制选择器；
- `Action::PiForkDismiss` 仍在 `dispatch/router.rs:1427` 有路由；
- 但 `agent_view/input.rs::handle_input_inner` 中把按键/鼠标送入选择器的分派块不存在，
  事件直接穿透到下层普通输入处理。

用户可见后果：`/fork` 打开后 Enter 确认、Esc 取消、`j`/`k`/方向键导航、鼠标点选全部无效；
只有滚轮还能移动光标，因为滚轮走的是 `agent_view/panes.rs:608` 另一条路径。

### 丢失点定位

`git log -S handle_fork_picker_key` 查不到删除提交，因为丢失发生在合并提交中（`-S` 默认不追溯 merge diff）。
按提交逐个统计符号出现次数后定位：

| 提交 | `handle_fork_picker_key` 出现行数 |
|---|---|
| `e4461c68` 引入 Pi 消息级 `/fork` | 9 |
| `32cb4c9f` Merge upstream a5589e9 | 8 |
| `HEAD` | 8 |

少掉的一行正是 `input.rs` 中的 `self.handle_fork_picker_key(key)`。
`32cb4c9f` 对应 [`docs/issues/架构/20260807-合并上游 a5589e9.md`](../架构/20260807-合并上游%20a5589e9.md)，
该记录中明确写明 20 个预演冲突"集中在 Pager input/render/viewer/app_view/dashboard"，
接缝是在 `input.rs` 的冲突解析中被漏掉的。

## 验收标准 (Acceptance Criteria)

- [x] `input.rs::handle_input_inner` 恢复 fork 选择器的键盘与鼠标分派块，位置与合并前一致（jump 块之后、CancelTurn 卡片之前）。
- [x] 分派块适配现有 API：活动判定用 `stoppable_activity_running() || any_cancel_pending()`，取消走 `handle_agent_action_with_registry`。
- [x] Ctrl+Q 继续放行给全局退出，不被选择器吞掉。
- [x] 三个 `dead_code` 警告消失，且不是靠 `#[allow]` 掩盖。
- [x] 新增回归测试覆盖 Enter 确认、Esc 取消、`j`/`k` 导航与 Ctrl+C 取消逃生口。
- [x] `check -p xai-grok-pager-bin --bin grok-pi` 与相关 lib 测试通过。

## 关键决策

| 决策 | 理由 |
|---|---|
| 忠实还原合并前的分派块，而非重新设计 | 该块与 `/jump` 同构，偏离会引入新的输入优先级差异 |
| 保留 `dismiss_fork_picker_if_suppressed()` 前置守卫 | 与合并前行为一致；`fork_slot_taken()` 的语义由它单点承载 |
| 用回归测试而不是注释锁住接缝 | 上游合并冲突只会重复发生，测试是唯一能在合并时报警的手段 |

## Notes

同批警告中另有几类，性质与本 Issue 不同，不要混为一谈：

- `dispatch_send_prompt_now` + `arm_send_now_and_paint_dispatched`：`ff2af3d3` 已用队列流程整体取代并删除，
  合并 `963ccf5c` 从上游侧把定义带了回来却没有调用方，属于合并复活的死代码。
- `handle_tree_map_loaded` + `dispatch_tree_map_closed`：自 `ecf2a6ae` 引入起就没有调用方。已确认**不是**丢失接线，
  而是重复实现——`/tree-map` 的加载由共享的 `handle_session_tree_loaded` 承担（`tree.rs:217` 已有
  `ActiveModal::TreeMap` 分支，且额外带 `count > 200` 的提示），关闭由 `dispatch_session_tree_closed` 承担
  （`tree.rs:126` 同时匹配 `SessionTree` 与 `TreeMap`）。两者接在 `task_result.rs:454` 与 `router.rs:306` 上，
  功能完好；这两个未使用函数是能力更弱的副本，可安全删除。
- `sync_timeline_appearance`：仅 `event_loop.rs` 测试在用。
- `Platform::Linux` / `Windows`：`current_platform()` 使用 `#[cfg(target_os)]` 分支，macOS 构建下必然报，非问题。
