1. **Pi 自有轻量 config 契约（推荐）**：新 `PiSessionConfig` 只携带 Pi 实际读的字段（模型/provider/端点/超时/压缩阀值等），`grok-pi` 与 adapter 改吃新契约；Stock 的 `AgentConfig` 不变。代价：adapter/pager 配置读取层需成批改写，收益是三个 crate 真退出。
2. **Pi 放弃 Stock Agent 浏览与 Sampler 复用**：把 `resolve_agent_definition`、aux 模型 `SamplerConfig` 解析在 Pi profile 下关掉（agents modal 在 Pi 下已是空列表，`build_agent_list` / `format_agent_detail` 已有 `cfg(not(stock-agent))` 分支），仍需处理 `GrokComConfig`/`SkillsConfig` 字段。代价：Pi 侧失去部分 Stock 能力对等；收益：改动面小于路径 1。

**单 crate 逐步退出也被依赖图堵死（逐个实测）**：

- `xai-grok-sampler`：被 `xai-grok-http`（`src/lib.rs` 2 处）、`xai-grok-telemetry`（`src/http.rs` 1 处）、`xai-grok-login`（`credential_provider.rs` + `attribution.rs` 共 12 处）以**非 optional 硬依赖**引用；`http` / `telemetry` 是 Pi 必需品，所以即使 shell 把 sampler 降为 optional，sampler 仍留在闭包里。仅 sampl 自身的 Pi 侧消费面就还有 `agent/config.rs`(11)、`tools/config.rs`(6)、`session/helpers/*`(2)、`session/summary.rs`(1)、`agent/chat_modes.rs`(1)、`agent/otel_gate.rs`(1) 等未门控点。
- `xai-grok-login`：`AuthManager` 是运行时类型（非纯数据），Pi 闭包内仍有 **224 行 / 52 文件**引用；`GrokComConfig` 及其嵌套 `OidcAuthConfig` / `OAuth2ProviderConfig` / `ForceLoginTeam` / `PreferredAuthMethod` 确实是纯 serde 数据（已验证），但只下沉它们不够——`AgentConfig` 的 `create_auth_manager() -> AuthManager` 仍把 login 钉在闭包里。

**关于 `Cargo.lock` 的好消息**：已核对锁文件，`xai-grok-shell` 的 lock 依赖列表本来就包含这三个 crate，而 optional 化不改变包解析图（`stock-agent` 仍是可启用路径），**因此降 optional 本身不需要刷新 `Cargo.lock`**。也就是说锁文件不是阻塞点——阻塞点只是那 96 个消费方文件的契约迁移量。

**sampler 的 trait 耦合（退出难度真正所在）**：`login ↔ sampler` 不是数据依赖而是契约依赖。`xai-grok-login/src/credential_provider.rs` 实现 `xai_grok_sampler::BearerResolver` 并返回 `SharedBearerResolver`；`attribution.rs` 实现 `Auth401AttributionCallback` 与 `SamplingConsumer`。而 `http` / `telemetry` 对 sampler 的依赖反而很浅——只有 `pub use xai_grok_sampler::OriginClientInfo;`（一个 `product: String` + `version: Option<String>` 的纯结构体，定义在 `sampler/src/config.rs:197`）。

因此**退出`xai-grok-sampler` 的最小完整路径**已可写成明确的工程清单（也是本批未做、留待授权的部分）：

1. `OriginClientInfo` 下沉并在 `http` 内定义，`sampler` / `telemetry` 改为 re-export → `http`、`telemetry` 两条依赖边断开（锁文件各删一项）；
2. `BearerResolver` / `Auth401AttributionCallback` / `SamplingConsumer` / `SharedBearerResolver` 下沉到纯 trait crate → `login` 的 12 处引用改向（锁文件改边）；
3. 处理 shell 残余 22 处（`agent/config.rs` 11、`tools/config.rs` 6、`session/helpers/*` 2、`session/summary.rs` 1、`agent/chat_modes.rs` 1、`agent/otel_gate.rs` 1）；
4. `shell` / `login` / `http` / `telemetry` 的 sampler 依赖改 `optional` + `stock-agent` 传递；
5. 手工同步 `Cargo.lock` 四处依赖边（步骤 1、2 改边、步骤 4 不改图）后由 CI `--locked` 实证。

预期收益（实测修正后）：只剩 `xai-grok-sampler` 本身（第 1 节记录的 `40.11s`）。原本预期的 `xai-grok-sampling-types`(15.90s) + `async-openai`(8.44s) **不会**随之退出——已核对依赖图，`xai-grok-sampling-types` 被 `xai-chat-state`、`xai-compaction-transcript`、`xai-grok-agent`、`xai-grok-subagent-resolution`、`xai-grok-shell` 共 6 个 crate 共用，sampler 退出后它仍在闭包里。

**方法论教训（供后续批次复用）**：

- 手工/静态扫描会漏三类引用：`super::` 相对路径、裸名 re-export（`pub use self::x::*` 后按 `session::NAME` 使用）、以及 **feature 链隐含关系**（`stock-mcp` 是否已隐含 `stock-agent`）。本批最终采用「消费方全量路径 × 定义处门控状态」双向对照扫描，才把 `MEMORY_MODE_META_KEY` 这类仅经星号 re-export 暴露的项抓出来。

- 门控改动必须成对核对「被门控模块 ← 谁引用它」和「Pi 侧是否还依赖该符号」，`resolve_agent_definition` 与 `MEMORY_MODE_META_KEY` 都是第二类问题的实例。
- 禁止在尚未证明编译面时派发昂贵的 macOS 验证；先 Linux 边界步、再 ARM64 是这轮唯一有效的止损策略。

**本轮新增的方法论教训**：

- 门控一个别名会连带门控所有隐式构造点。`Client = SamplingClient` 门控后，任何 `#[cfg(test)]` 模块里 `OaiCompatClient::new(...)` 都会在下一轮 CI 才炸；翻转前应一次性扫 `SamplingClient::new|OaiCompatClient::new|SummaryGenerator::new` 的测试面，而不是逐个等 CI 报。
- `pub use` 的重名冲突（E0252）只在编译期出现。轻类型块与运行时块**不能同时**导出同一个名字，即使它们指向同一个底层类型。
- 静态门控扫描要把「模块声明所在文件」也纳入上溯，否则会把 `acp_session` 这类整模块门控的子模块误判为 Pi 编译面（本轮的首版扫描即如此误报）。

#### 为什么 login 退出会撞上「受保护能力不可拆」（2026-11-19 最终定论）

第三次尝试的 80 个错误里，有一半不是我的切口写错，而是指向同一个结构事实：**Pi 自己的会话列表路径就在调用 Stock 的远端会话组件**。

```text
session/unified_list/mod.rs:6   use crate::remote::{ConvError, ConvQuery, ConversationsClient};
session/unified_list/mod.rs:5   use crate::agent::session_registry_client::SessionRegistryClient;
session/unified_list/mod.rs:389  remote: Vec<crate::agent::session_registry_client::SessionRecord>
session/unified_list/facets.rs:7 use crate::remote::Conversation;
session/unified_list/row.rs:8    use crate::remote::Conversation;
session/merge.rs:14              use crate::agent::session_registry_client::{SessionRecord, SessionRegistryClient};
session/storage/summary_write.rs:22 use crate::session::worktree::WorktreeIdentity;
agent/config.rs:2                use crate::agent::model_providers::{...};
agent/model_providers.rs         PROVIDER_TOKEN_EXPIRY_SKEW_SECS / PROVIDER_TIMEOUT_CEILING_SECS
```

`session::unified_list` 是 Pi 的会话列表界面数据源（pager 侧 6 处引用），`session::merge` 合并远端 registry 记录，`summary_write` 记录 worktree 身份。把这些改成 `#[cfg(not(feature = "stock-agent"))]` 的降级实现，等于在 Pi 里删掉远端会话、worktree 归属与 registry 合并——正是硬约束里「受保护能力不可拆」禁止的事。

因此 login（以及同样经由 session 层引用 `AgentDefinition` 的 agent）退出 Pi 闭包，**不是 cfg 工程问题，而是产品能力取舍**。可执行的下一步只有两个，都需要授权：

1. 在 Pi 里正式放弃远端会话/registry/worktree 归属能力，然后按本轮清单完成门控；
2. 把 `session` 的 Stock 远端组件拆成独立 crate（`xai-grok-session-stock`），Pi 只依赖 slim 的本地会话层——这是本文一直说的 L4 路径。

本轮已把可以安全落地的部分落地（sampler 退出 + 认证纯数据下沉），其余按上述结论停手，回滚到绿点 `892b4283`。

#### 第四次尝试（自动门控）：76 个错误，证明「按错误行自动切函数」不可行

第三轮失败后改用自动门控：把 CI 报出的每个错误位置所属的 `use` 行与最内层 `fn` 直接加 `stock-agent`。结果又得到 **76 个错误**，并且相当一部分是自伤：

| 症状 | 原因 |
|---|---|
| `cannot find type GrokComConfig`（4） | 自动门控把 **已下沉类型** 的 import 也切了，未门控代码随即丢失类型 |
| `cannot find function walk_toml / resolve_credentials_enforced / new_from_toml_cfg`（11） | 被切的函数是 Pi 与 Stock 共用的解析/构造入口 |
| `cannot find type SessionRecord / SessionRegistryClient`（12） | 这些类型由 `session_registry_client` 提供，而该模块本身已被门控 |
